# PrintLink Security / Threat Model

PrintLink is designed for small trusted office LANs. This document states
what it protects, what it does **not** protect against, and the reasoning
behind the storage layout.

## Data layout

| Item | Location | Contains |
|---|---|---|
| `printlink.db` | `%PROGRAMDATA%\PrintLink` (shared) | printers, grants, **pairing tokens** |
| `identity.json` | `%PROGRAMDATA%\PrintLink` (shared) | this PC's public ID (`pc_id`) |
| `target.json` | `%PROGRAMDATA%\PrintLink` (shared) | last selected remote printer |
| logs | `%PROGRAMDATA%\PrintLink` | job metadata, sender/host IDs |

If the shared dir is not writable (e.g. an ACL misconfiguration), the agent
falls back to the per-user `%LOCALAPPDATA%\PrintLink` — with the consequence
that each Windows account then sees only its own printers.

The shared dir is machine-wide **on purpose**: a PC is one PrintLink identity,
and every user account on it must see the same printers and grants. The
installer explicitly grants `Users:(OI)(CI)M` on `%PROGRAMDATA%\PrintLink`.

## What a pairing token is

A token is generated by the **host** when it accepts a share request and is
stored in the host's `grants` table and the sender's `remote_printers` table.
It is both:

1. **Authorization** — the host accepts a `/print` job only if
   `X-Token` matches the `grants` row for that sender ID (shares.py).
2. **The AES-GCM key** for the job payload (crypto.py) — anyone holding the
   token can decrypt any job between those two PCs.

## Threats on a shared PC (local user B vs. user A's data)

Both tables containing tokens live in `%PROGRAMDATA%\PrintLink`, which any
local user can read **and write** (required by the design, see below):

- **T1 — Token theft (read).** B reads A's `grants` / `remote_printers`
  tokens. With a token B can print to A's printer without A's knowledge, and
  can decrypt captured job payloads (see T4).
- **T2 — Grant injection (write).** B inserts a row into the host's `grants`
  table with a token B chooses. The host then accepts B's `/print` requests
  with that token — **no accept dialog is shown**. Same effect as a forged
  acceptance.
- **T3 — Tampering.** B can rename/remove printers, alter grants/expiry,
  replace `target.json`, or delete the DB entirely (denial of service).
- **T4 — LAN capture.** Jobs travel AES-GCM-encrypted, but the key is the
  token (see T1). On a switched LAN, passive capture of a *specific* job
  requires ARP spoofing / MITM; the realistic exposure is reading the DB.

## Why write access is granted to all local users

PrintLink agents run per-user at login. On a shared PC any account may act as
a sender (writes its `remote_printers` tokens) or as a host (writes `grants`
when accepting). Restricting DB writes to SYSTEM/Admins would silently push
non-admin accounts back onto per-user data — recreating the "right-click does
nothing" bug. The trade-off is deliberate: **local users are trusted**.

Reasonable mitigations for deployments that care:

- Allow only trusted people to log in locally; standardize on admin-managed
  user accounts (the token DB is then effectively admin-only).
- Enable BitLocker / full-disk encryption (protects the DB at rest).
- Keep the PC patched — T1/T2 are moot once remote code execution or
  credential theft is possible anyway.
- If a fully multi-tenant design is needed, see the hardening plan below.

## Planned hardening (not yet implemented)

**Split the database:** shared, read-mostly tables (`printers`) in
`%PROGRAMDATA%\PrintLink`; token-bearing tables (`grants` on the host,
`remote_printers` on senders) in per-user `%LOCALAPPDATA%\PrintLink`. Tokens
then become readable only by the account that owns them, and a local user can
no longer inject grants into another account's host. Requires a schema split
and migration, and a decision on how a per-user host is discovered by senders;
not done yet.

## Report a vulnerability

Open an issue on https://github.com/najm07/Printlink/issues and mention
"security" — this is a hobby LAN tool; fix priority is low unless the
exposure is remote.
